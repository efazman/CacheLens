STEP 2 — BENCHMARK SIZING
=============================================================================
benchmarks/matrix_bad.cpp and benchmarks/matrix_good.cpp were hardcoded to
N=1024 (working set = 3 * 1024^2 * 8 bytes = 25,165,824 bytes ~= 24 MiB,
which fits inside the 32 MiB L3 and collapses the good/bad separation).

Changed both to N=2400:
  Per matrix:    2400^2 * 8 bytes        = 46,080,000 bytes  ~= 43.95 MiB
  Three matrices: 3 * 46,080,000 bytes   = 138,240,000 bytes ~= 131.8 MiB
  Working set / L3 ratio: 131.8 MiB / 32 MiB ~= 4.12x

=============================================================================
STEP 3 — VECTORIZATION CHECK
=============================================================================
Built both at -O2 with -fopt-info-vec-optimized:

  matrix_bad.cpp:41:31: optimized: loop vectorized using 16 byte vectors
  (matrix_good.cpp: no vectorization message)

Disassembly (objdump -d -M intel) of the -O2 binaries confirmed:
  - matrix_bad inner k-loop: vectorized. Uses `mulpd` (packed multiply),
    processing 2 k-iterations per pass. The contiguous A[i][k] access
    became a single packed load (`movupd`). The strided B[k][j] access
    (stride = N*8 = 19200 bytes) is built from two SEPARATE scalar loads
    (`movsd` + `movhpd` at +0x4b00) packed into an xmm register — there is
    no gather instruction, so the number of distinct cache lines touched
    for B is unchanged, but the arithmetic/loop overhead is halved
    relative to a true scalar build.
  - matrix_good inner j-loop: NOT vectorized (stayed fully scalar —
    movsd/mulsd/addsd, one double at a time). GCC could not prove
    A/B/C don't alias (no `restrict`), which blocked auto-vectorization
    of the read-modify-write into C.

Decision: since matrix_bad's hot loop was vectorized at -O2 and matrix_good's
was not, this is an asymmetric confound relative to what the source implies
("naive scalar i-j-k" vs "cache-friendly scalar i-k-j"). Rebuilt both at
-O1. Confirmed via -fopt-info-vec-optimized (no messages for either) and
objdump (zero occurrences of mulpd/movupd/movdqa/movdqu in either -O1
binary) that both are fully scalar at -O1.

Settled on: -O1 for both matrix_bad and matrix_good.
Build commands:
  g++ -O1 -g -fno-omit-frame-pointer -no-pie -std=c++17 -o matrix_bad matrix_bad.cpp
  g++ -O1 -g -fno-omit-frame-pointer -no-pie -std=c++17 -o matrix_good matrix_good.cpp

=============================================================================
STEP 4 — MEASUREMENT
=============================================================================
Command per binary, run individually 5 times (not perf's internal -r
aggregation) so raw per-run values could be captured for manual mean/stdev:

  perf stat -x, -e cache-misses,cache-references,instructions,cycles \
      -o <file> --append ./<binary>

Scope note (do not blur): perf stat wraps the entire process from exec to
exit — this includes init() (heap allocation of 3 arrays, ~11.52M rand()
calls to fill A and B, and a memset of C), not just the multiply hot loop.
Wall-clock (both the shell `time` command and perf's own elapsed-time
field) covers the SAME whole-process scope as the perf counters — they are
not mismatched in scope. Measured in isolation, init() takes ~0.071s
(3 runs: 0.0709s, 0.0712s, 0.0725s), which is ~0.6% of matrix_bad's total
wall time and ~1.3% of matrix_good's — small but not zero, and identical
between the two binaries since init() is unmodified shared code.
